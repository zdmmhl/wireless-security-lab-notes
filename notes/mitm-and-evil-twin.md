## Part A: Man-in-the-Middle Attack

### Objective

The purpose of Part A was to demonstrate a man-in-the-middle attack on an unencrypted HTTP connection. In this exercise, a Raspberry Pi acted as a rogue wireless access point and transparent proxy, while a mobile device acted as the victim client. The goal was to intercept the HTTP login traffic and recover the username and password transmitted in plaintext.

### Experimental Setup

The Raspberry Pi provided the wireless access point and hosted a local login page. After connecting to the AP, I accessed the Pi through SSH and configured the system so that traffic from the victim device would be redirected into `mitmproxy`.

The basic workflow was as follows:

1. Connect to the Raspberry Pi access point.
2. Access the Pi using SSH.
3. Configure a unique SSID to avoid conflict with other groups.
4. Enable IP forwarding on the Pi.
5. Add `iptables` NAT redirection rules for ports 80, 443, and 3000.
6. Start the local web server using `node login.js`.
7. Open a second terminal and run `mitmproxy` in transparent mode.
8. Use the mobile phone to browse to the fake login page.
9. Submit credentials and observe the captured HTTP request in `mitmproxy`.

### Key Commands Used

The main commands used during the experiment are listed below.

```bash
ssh pi@192.168.4.1
/sfwn/wifi-setting.sh reset <new-SSID>
sudo sysctl -w net.ipv4.ip_forward=1
sudo iptables -t nat -A PREROUTING -i wlan0 -p tcp --dport 80 -j REDIRECT --to-port 8080
sudo iptables -t nat -A PREROUTING -i wlan0 -p tcp --dport 443 -j REDIRECT --to-port 8080
sudo iptables -t nat -A PREROUTING -i wlan0 -p tcp --dport 3000 -j REDIRECT --to-port 8080
cd /sfwn/login/
node login.js
mitmproxy --mode transparent --showhost
```

### What Each Step Achieved

`ssh pi@192.168.4.1` was used to obtain remote shell access to the Raspberry Pi after joining its wireless access point.

`/sfwn/wifi-setting.sh reset <new-SSID>` changed the access point name so that it would not conflict with other groups in the lab room.

`sudo sysctl -w net.ipv4.ip_forward=1` enabled packet forwarding so that the Pi could relay client traffic instead of simply receiving it.

The three `iptables` commands redirected TCP traffic arriving on `wlan0` for ports 80, 443, and 3000 into the local proxy listening on port 8080.

`node login.js` started the local login page hosted on the Raspberry Pi.

`mitmproxy --mode transparent --showhost` launched the transparent proxy and allowed inspection of the captured flows.

### Observations

After completing the setup, I connected my phone to the rogue wireless network and opened the login page at:

```text
https://lab.example.invalid
```

The browser displayed a login form asking for a username and password. I entered my zID as the username and `kali` as the password. The login attempt failed because the page was only a dummy credential capture page, but the network request was still sent over HTTP.

In the `mitmproxy` window, the HTTP flow list showed the traffic generated by the mobile device. After selecting the relevant POST request to `login-page.com`, the credentials were visible in the request body in URL encoded form. This demonstrated that sensitive information sent through unencrypted HTTP can be intercepted and read directly by an attacker positioned in the middle.

### Result

The experiment was successful. I was able to:

1. configure the Raspberry Pi as a transparent MITM device,
2. redirect the victim's traffic into `mitmproxy`, and
3. locate the POST request containing the submitted username and password.

This confirms the core security lesson of the lab: if a login form uses plain HTTP instead of HTTPS, an attacker on the path can capture credentials without needing to break encryption.

### Security Discussion

This attack worked because the communication was not protected by transport layer encryption. Even though the user interacted with what looked like a normal login page, the credentials were exposed in the HTTP request body and could be read immediately by the attacker. In a real environment, this type of weakness could lead to account compromise, password reuse attacks, and loss of privacy.

The experiment also showed why transparent proxying is dangerous. The victim device did not need to configure any proxy settings manually. All traffic was redirected at the network layer by the attacker, which makes this kind of attack realistic in a hostile wireless environment.

## Part B: Evil Twin Access Point

### Overview

Part B is a theoretical extension of Part A. In Part A, the victim voluntarily connected to the attacker's rogue access point. In practice, this may not always happen. A more realistic attack is an **evil twin** attack, where the attacker creates a fake access point that impersonates a legitimate wireless network and then tricks nearby clients into reconnecting to it.

In the lab scenario, the legitimate network is:

- SSID: `CafeGuest`
- Channel: `5`
- Encryption: none, meaning it is an open Wi Fi network

Because the target network is open and does not require authentication, it is easier for an attacker to imitate it.

### How the Attack Works

An evil twin attack works by creating a second access point that uses the same SSID as the legitimate network. The attacker then causes the victim device to disconnect from the real access point. Once disconnected, the victim device searches for another network with the same SSID and may automatically associate with the stronger or more convenient signal, which can be the attacker's access point.

After the victim joins the evil twin, the attacker provides network services such as DHCP so that the client receives an IP address and can continue communicating. To avoid making the attack obvious, the attacker also forwards the victim's traffic onward to the real Internet connection. As a result, the victim usually continues browsing normally and may not notice that all traffic is now passing through the attacker's system.

### Why This Attack Is Effective

The main reason this attack is effective is that the victim often sees nothing unusual. The SSID looks familiar, the device reconnects automatically, and Internet access still appears to work. If the network is open, there is no cryptographic proof that the access point is genuine. This makes it possible for the attacker to impersonate the café network convincingly.

Compared with Part A, this scenario is more realistic because the attacker does not need to wait for the victim to choose the rogue network manually. Instead, the attacker actively forces the transition from the legitimate AP to the evil twin.

### Typical Attack Sequence

A typical evil twin attack proceeds in the following stages:

1. The attacker observes the legitimate access point and copies its SSID.
2. The attacker creates a rogue access point using the same SSID.
3. The attacker causes clients to disconnect from the legitimate AP, commonly by sending forged deauthentication or disassociation frames.
4. The victim reconnects to the rogue access point because it appears to be the expected network.
5. The rogue access point issues network configuration to the victim, such as an IP address.
6. The attacker forwards the victim's traffic to the Internet so that connectivity appears normal.
7. The attacker monitors, captures, or manipulates the victim's traffic.

### Risks to the Victim

Once connected to the evil twin, the victim's traffic can be observed, modified, or redirected. The attacker may capture plaintext logins, inject fake pages, force HTTP downgrade behaviour, or direct the victim to malicious sites through DNS manipulation. If the victim enters passwords into a fake captive portal or insecure login page, those credentials can be stolen.

This type of attack is especially dangerous on public Wi Fi because users often assume that a familiar network name is trustworthy. In reality, the SSID alone does not prove authenticity.

### Defensive Considerations

Users can reduce the risk of an evil twin attack by avoiding open public Wi Fi when possible, preferring mobile data or a trusted VPN, and being cautious when a device suddenly reconnects or prompts for login again. HTTPS warnings, certificate errors, repeated captive portal prompts, and unusually weak or unstable connectivity can all be warning signs.

From a network administration perspective, stronger protection is achieved by using authenticated wireless security instead of open Wi Fi, disabling insecure fallback behaviour where possible, and educating users not to trust a network based only on its name.
